# Recovery acceptance

Reviewed 13 November 2026 Sydney. This is a recovery runbook and evidence register, not certification that production data has been restored. Current application identity and checks live in docs/audit/queue-2026-11-13.json; earlier advisory observations below remain dated snapshots.

| Layer | Current evidence | Remaining proof |
| --- | --- | --- |
| Code | The current published runtime, exact CI results, domains and rollback deployment are recorded in the active queue release object. Tested application deployments remain available for code rollback. | Assign both domains to the selected known deployment, verify the runtime and rerun public checks. A branch push alone does not prove that custom domains moved. |
| Saved plans/workspaces | Handler tests exercise owner checks, exact revisions, uncertain receipts, conflicts, retries and recoverable entry removal. No production records were changed. | Confirm backup date/retention and restore synthetic trip rows to an isolated project, then open and edit them through the app. No hosted restore is claimed. |
| Private files | Handler tests exercise stored content hashes, owner checks, range downloads, MIME validation, finalisation and recoverable deletion states. | Restore both storage object bytes and corresponding database rows into isolation. Match byte size and SHA-256, then authenticate as owner and another user to test download denial. |

Supabase database backups include Storage metadata, not the stored object bytes. Follow the [official backup guide](https://supabase.com/docs/guides/platform/backups) and [object download guide](https://supabase.com/docs/guides/storage/management/download-objects). A database rollback alone cannot recover deleted files.

Never run restore commands against the live project as a test. Record the exact source snapshot, object manifest, environment, results, recovery time and reviewer before marking data recovery complete. Keep backups encrypted and private. Do not attach customer data to Git or CI artifacts.

An earlier read-only advisory snapshot of AVES Shared Accounts on 13 November found no health advisories. Security advisories show informational RLS-with-no-policy notices on private server-only tables, plus disabled leaked-password protection. Deny-all RLS must not be weakened to clear an informational notice. Password protection remains an explicit configuration follow-up, not a completed fix. [Supabase guidance](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
